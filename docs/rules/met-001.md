# MET-001 — metric attributes have bound cardinality

**Impact:** Important (weight 30) · **Target:** metric · **Source:** spec ·
**Confidence:** poller-verifiable (`mimir_label_cardinality`)

Attribute keys on metrics, aggregated by metric name, MUST have fewer than
10,000 unique values within a 1-hour window (spec default; tune via
`params.max_cardinality`). High-cardinality attributes explode active series —
the dominant cost and performance failure mode of Prometheus-family backends.

**Detection.** The sampled stream feeds one HyperLogLog sketch per
(service, metric, attribute) — estimates, never exact sets, with a hard cap on
tracked pairs (overflow is reported in the report notes, not silently
dropped). The Mimir poller re-checks each flagged pair against the
cardinality API (`label_values_count`, active series, scoped to the service's
`job`), which sees the unsampled stream. The pairs are combined per service:
any pair over the limit fails the rule, and the verdict upgrades the finding to
`verified`. The pair is queried under the names Mimir stores it as: the OTLP
name with dots turned into underscores, with or without the unit and type
suffixes the pipeline adds (`http.server.duration` in `ms` is found as
`http_server_duration_milliseconds_bucket` or `http_server_duration_bucket`),
and the attribute as a label (`url.full` as `url_full`). A pair Mimir has no
series for under either name (a metric only on the sampled stream) is not
measured, and the sampled result stands. Requires `cardinality_analysis_enabled:
true` on the tenant (the kind dev cluster enables it).

**Remediation.** Drop or hash the attribute at the collector (template
`high-cardinality-attribute`, scoped to the service); typical offenders:
user IDs, request IDs, raw URLs.
